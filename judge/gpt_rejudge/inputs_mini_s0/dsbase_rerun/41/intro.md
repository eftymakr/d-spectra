## Related Works

Serverless computing has become a prevailing cloud paradigm due to its abstraction of server management, automatic scaling, and cost-efficiency by charging only for actual resource usage \[[2406.11734v1](http://arxiv.org/abs/2406.11734v1)\]. Despite these benefits, cold-start latency—delays caused when launching new function instances—remains a fundamental challenge impairing the overall performance and user experience in serverless environments \[[1903.12221v1](http://arxiv.org/abs/1903.12221v1)\]. This latency primarily stems from the initialization overhead of runtime containers, library loading, and function code execution, particularly exacerbated in Python-based functions due to inefficient library initialization patterns \[[1810.05633v2](http://arxiv.org/abs/1810.05633v2)\].

Early efforts to mitigate cold starts have focused on infrastructure-level strategies such as maintaining pools of warm containers to serve incoming requests without the delay of cold initialization. For example, a pool-based approach on Knative Serving demonstrated up to an 85% reduction in the 99th percentile response latency by reusing pre-warmed containers \[[2304.00396v1](http://arxiv.org/abs/2304.00396v1)\]. Extending this idea, Pagurus introduced inter-action container sharing, which allows function invocations to borrow warm containers from similar actions, effectively eliminating cold startup times and reducing startup latency to as low as 10 ms \[[2108.11240v1](http://arxiv.org/abs/2108.11240v1)\]. These container reuse techniques address cold starts from a resource management perspective but do not directly optimize application-level inefficiencies.

At the application level, code loading latency has been identified as a significant contributor to cold-start delays. FaaSLight addresses this by constructing function-level call graphs to separate indispensable from optional code, loading only the necessary components at startup and deferring optional code loading. This method achieved up to 78.95% reduction in code loading latency and a 42.05% reduction in total response latency, highlighting the importance of application-level optimizations \[[2207.08175v2](http://arxiv.org/abs/2207.08175v2)\]. Complementary to static code separation, LibProf employs dynamic profiling to identify inefficient library initializations in Python serverless applications using statistical sampling and call-path profiling, achieving up to 2.26x speedup in cold-start execution time and 1.51x memory usage reduction \[[1810.05633v2](http://arxiv.org/abs/1810.05633v2)\]. SLIMSTART builds upon these insights by integrating dynamic profiling with automated code transformations, thereby addressing workload-dependent inefficiencies that static analysis alone cannot detect.

Machine learning and predictive methods have also been proposed to proactively mitigate cold starts by anticipating function invocation patterns and preparing resources in advance. Temporal Convolutional Networks (TCN) have been used to forecast function instance arrivals 10–15 minutes ahead, enabling better resource provisioning and outperforming traditional ML approaches for time series prediction in serverless clouds \[[2207.08175v2](http://arxiv.org/abs/2207.08175v2)\]. Reinforcement learning techniques, such as off-policy Q-learning, have been applied to decide when to pre-initialize function instances based on CPU utilization and failure rates, yielding improvements in throughput and reductions in resource waste by up to 55% and 37%, respectively \[[2210.15831v1](http://arxiv.org/abs/2210.15831v1)\]. SPES further refines this by categorizing functions based on invocation patterns and applying granular pre-loading/unloading strategies, reducing cold start rates by nearly 50% and wasted memory time by over 56% .

Proactive function resource management approaches like “freshen” allow developers or providers to specify preparatory steps before function execution to mitigate overheads and improve responsiveness \[[2010.04312v1](http://arxiv.org/abs/2010.04312v1)\]. Similarly, HydraServe targets cold-start latency in serverless deployment of large language models by strategically distributing models and overlapping cold-start stages, achieving latency reductions between 1.7x and 4.7x \[[2502.15524v2](http://arxiv.org/abs/2502.15524v2)\].

Comprehensive reviews and taxonomies of cold-start mitigation techniques classify solutions into caching, application-level optimization, container reuse, and AI/ML-based approaches while highlighting the persistent challenge of balancing resource efficiency with latency reduction \[[2310.08437v2](http://arxiv.org/abs/2310.08437v2)\]. SLIMSTART contributes to this landscape by focusing on the previously underexplored area of workload-dependent library usage inefficiencies, combining dynamic profiling and automated optimization within CI/CD pipelines to adapt to evolving workloads, thus providing improved initialization and end-to-end latency reductions alongside memory savings.

In summary, related work spans infrastructure reuse strategies \[[2108.11240v1](http://arxiv.org/abs/2108.11240v1)\]\[[2304.00396v1](http://arxiv.org/abs/2304.00396v1)\], application-level code loading optimizations \[[1810.05633v2](http://arxiv.org/abs/1810.05633v2)\]\[[2207.08175v2](http://arxiv.org/abs/2207.08175v2)\], predictive and adaptive resource management through machine learning \[[2207.08175v2](http://arxiv.org/abs/2207.08175v2)\]\[[2210.15831v1](http://arxiv.org/abs/2210.15831v1)\], and proactive execution preparation \[[2502.15524v2](http://arxiv.org/abs/2502.15524v2)\]\[[2010.04312v1](http://arxiv.org/abs/2010.04312v1)\]. SLIMSTART advances this body of research by targeting dynamic library usage inefficiencies with profile-guided transformations, complementing existing approaches with fine-grained, workload-aware cold-start optimizations.

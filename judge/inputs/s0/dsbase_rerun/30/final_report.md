## Related Works

Modern database systems often trade strong transaction isolation guarantees for weaker ones to achieve low latency and high throughput \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. This trade-off has led to the emergence of isolation bugs, which can compromise data consistency \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. Black-box testing has become a prominent technique for detecting these bugs by verifying whether transaction histories adhere to specified isolation levels \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. However, testing large-scale databases remains challenging due to the computational complexity of existing isolation checkers \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\].

Several approaches have been proposed to improve the efficiency of isolation testing. For instance, MTC introduces Mini-Transactions (MTs) to reduce overhead during history generation and verification \[[2' 2020-12-02](http://arxiv.org/abs/2012.01085v4)\]. By leveraging MTs' read-modify-write pattern, MTC achieves linear or quadratic time complexity for verifying strong isolation levels \[[2' 2020-12-02](http://arxiv.org/abs/2012.01085v4)\]. Similarly, CHRONOS and AION extend timestamp-based isolation checking to online settings, enabling efficient processing of large transaction histories \[[7' 2025-04-02](http://arxiv.org/abs/2504.01477v1)\]. These tools demonstrate significant performance improvements over traditional offline checkers \[[7' 2025-04-02](http://arxiv.org/abs/2504.01477v1)\].

In contrast, weak isolation levels such as Read Committed (RC), Read Atomic (RA), and Causal Consistency (CC) have been shown to be testable in polynomial time \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. This has enabled the development of scalable testing tools that can handle larger workloads \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. However, existing testers often exhibit high polynomial complexity, limiting their applicability to moderate-sized datasets \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. For example, MonkeyDB provides a mock storage system for testing applications against weak isolation levels by simulating all possible return values for read operations \[[3' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\]. This approach ensures comprehensive coverage of weak behaviors, which are rare but critical to application robustness \[[3' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\].

The work on AWDIT represents a significant advancement in this area. AWDIT is a highly-efficient and provably optimal tester for weak isolation levels, achieving time complexities of $O(n^(3/2))$, $O(n^(3/2))$, and $O(n \cdot k)$ for RC, RA, and CC, respectively \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. This improves upon the state of the art by reducing the computational overhead of existing testers \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. Furthermore, AWDIT is shown to be essentially optimal, as there is a conditional lower bound of $n^(3/2)$ for any weak isolation level between RC and CC \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\]. Experimental results demonstrate that AWDIT is significantly faster than existing, highly optimized testers, achieving speedups of up to $245\times$ for RC and $193\times$ for RA on large histories \[[1' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\].

[Snippet]: «Transactional isolation guarantees are crucial for database correctness. However, recent studies have uncovered numerous isolation bugs in production databases. The common black-box approach to isolation checking stresses databases with large, concurrent, randomized transaction workloads and verifies whether the resulting execution histories satisfy specified isolation levels.   We address these inefficiencies through the novel design of Mini-Transactions (MTs). MTs are compact, short transactions that execute much faster than general workloads, reducing overhead during history generation by minimizing database blocking and transaction retries. By leveraging MTs' read-modify-write pattern, we develop highly efficient algorithms to verify strong isolation levels in linear or quadratic time. Despite their simplicity, MTs are semantically rich and effectively capture common isolation anomalies described in the literature.
  We implement our verification algorithms and an MT workload generator in a tool called MTC. Experimental results show that MTC outperforms state-of-the-art tools in both history generation and verification. Moreover, MTC can detect bugs across various isolation levels in production databases while maintaining the effectiveness of randomized testing with general workloads, making it a cost-effective solution for black-box isolation checking.»

The isolation checking problem asks whether a given execution history of a database system satisfies a specified isolation level. Experiments highlight that CHRONOS processes offline histories with up to one million transactions in seconds, greatly outperforming existing SI checkers. Furthermore, AION and AION-SER sustain a throughput of approximately 12K transactions per second, demonstrating their practicality for online isolation checking.»

[Snippet]: «Consistency guarantees among concurrently executing transactions in local- and distributed systems, commonly referred to as isolation levels, have been formalized in a number of models. Thus far, no model can reason about executable implementations of databases or local transaction libraries providing weak isolation levels. Weak isolation levels are characterized by being highly concurrent and, unlike their stronger counterpart serializability, they are not equivalent to the consistency guarantees provided by a transaction library implemented using a global lock. Industrial-strength databases almost exclusively implement weak isolation levels as their default level. This calls for formalism as numerous bugs violating isolation have been detected in these databases. In this paper, we formalize three weak isolation levels in separation logic, namely read uncommitted, read committed, and snapshot isolation. We define modular separation logic specifications that are independent of the underlying transaction library implementation. Historically, isolation levels have been specified using examples of executions between concurrent transactions that are not allowed to occur, and we demonstrate that our specifications correctly prohibit such examples. To show that our specifications are realizable, we formally verify that an executable implementation of a key-value database running the multi-version concurrency control algorithm from the original snapshot isolation paper satisfies our specification of snapshot isolation. Moreover, we prove implications between the specifications -- snapshot isolation implies read committed and read committed implies read uncommitted -- and thus the verification effort of the database serves as proof that all of our specifications are realizable. All results are mechanized in the Rocq proof assistant on top of the Iris separation logic framework.»

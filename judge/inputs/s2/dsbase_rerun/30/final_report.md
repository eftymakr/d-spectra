## Related Works

Modern databases often trade strong transaction isolation for weak isolation guarantees to achieve low latency and high throughput \[[1' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\]. This trade-off has led to the emergence of isolation bugs in production databases, which can break data-consistency contracts \[[1' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\]. Black-box testing has become a prominent technique for detecting such bugs by verifying whether transaction histories adhere to prescribed isolation levels \[[1' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\].

Several studies have explored the complexity of isolation testing. Testing strong isolation levels has been shown to be NP-complete, while weak isolation levels can be tested in polynomial time \[[1' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\]. However, existing testers often have large polynomial complexity, limiting their applicability to moderate-sized workloads \[[1' 2021-03-04](http://arxiv.org/abs/2103.02830v1)\]. This has motivated the development of more efficient testing frameworks.

The work in \[[2' 2022-02-24](http://arxiv.org/abs/2202.12139v1)\] presents MonkeyDB, a mock storage system that supports multiple isolation levels and provides coverage of weak behaviors. It uses a logical specification of isolation levels to compute possible return values for read operations and randomly returns one of them. While MonkeyDB is effective for testing applications against weak isolation, it is not optimized for large-scale workloads.

In \[[3' 2025-04-03](http://arxiv.org/abs/2504.02344v1)\], the authors introduce Mini-Transactions (MTs) to improve the efficiency of black-box isolation checking. MTs are compact transactions that reduce overhead during history generation and enable efficient verification of strong isolation levels. This approach is particularly useful for production databases with high concurrency. However, it focuses on strong isolation levels and does not address the specific challenges of weak isolation testing.

The paper \[[4' 2025-01-24](http://arxiv.org/abs/2501.14421v2)\] formalizes three weak isolation levels—read uncommitted, read committed, and snapshot isolation—in separation logic. It defines modular specifications that are independent of the underlying transaction library implementation and demonstrates that these specifications can be realized by an executable implementation of a key-value database. This formalization provides a theoretical foundation for reasoning about weak isolation levels, but it does not address the practical challenges of testing them at scale.

In \[[5' 1999-04-15](http://arxiv.org/abs/hep-ph/9904350v1)\], the authors propose an algorithm for comparing trees labeled in an arbitrary manner, which is faster than previous methods. While this work is not directly related to database testing, it highlights the importance of efficient algorithms in handling complex data structures, which is relevant to the development of isolation testers.

[Snippet]: «Modern applications, such as social networking systems and e-commerce platforms are centered around using large-scale storage systems for storing and retrieving data. In the presence of concurrent accesses, these storage systems trade off isolation for performance. The weaker the isolation level, the more behaviors a storage system is allowed to exhibit and it is up to the developer to ensure that their application can tolerate those behaviors. ### <a id='category-black-box-testing-techniques-for-isolation'></a>Black-box Testing Techniques for Isolation: 1 papers found.

[Snippet]: «Transactional isolation guarantees are crucial for database correctness. However, recent studies have uncovered numerous isolation bugs in production databases. The common black-box approach to isolation checking stresses databases with large, concurrent, randomized transaction workloads and verifies whether the resulting execution histories satisfy specified isolation levels. For strong isolation levels such as strict serializability, serializability, and snapshot isolation, this approach often incurs significant end-to-end checking overhead during both history generation and verification.
  We address these inefficiencies through the novel design of Mini-Transactions (MTs). MTs are compact, short transactions that execute much faster than general workloads, reducing overhead during history generation by minimizing database blocking and transaction retries. By leveraging MTs' read-modify-write pattern, we develop highly efficient algorithms to verify strong isolation levels in linear or quadratic time. Despite their simplicity, MTs are semantically rich and effectively capture common isolation anomalies described in the literature.
  We implement our verification algorithms and an MT workload generator in a tool called MTC. Experimental results show that MTC outperforms state-of-the-art tools in both history generation and verification. Moreover, MTC can detect bugs across various isolation levels in production databases while maintaining the effectiveness of randomized testing with general workloads, making it a cost-effective solution for black-box isolation checking.»

### <a id='category-formalization-of-weak-isolation-levels'></a>Formalization of Weak Isolation Levels: 1 papers found.
Context: 
	Document 1: [_citation_number]: «4»
[Snippet]: «Consistency guarantees among concurrently executing transactions in local- and distributed systems, commonly referred to as isolation levels, have been formalized in a number of models. Thus far, no model can reason about executable implementations of databases or local transaction libraries providing weak isolation levels. Weak isolation levels are characterized by being highly concurrent and, unlike their stronger counterpart serializability, they are not equivalent to the consistency guarantees provided by a transaction library implemented using a global lock. Industrial-strength databases almost exclusively implement weak isolation levels as their default level. This calls for formalism as numerous bugs violating isolation have been detected in these databases. In this paper, we formalize three weak isolation levels in separation logic, namely read uncommitted, read committed, and snapshot isolation. We define modular separation logic specifications that are independent of the underlying transaction library implementation. Historically, isolation levels have been specified using examples of executions between concurrent transactions that are not allowed to occur, and we demonstrate that our specifications correctly prohibit such examples. To show that our specifications are realizable, we formally verify that an executable implementation of a key-value database running the multi-version concurrency control algorithm from the original snapshot isolation paper satisfies our specification of snapshot isolation. Moreover, we prove implications between the specifications -- snapshot isolation implies read committed and read committed implies read uncommitted -- and thus the verification effort of the database serves as proof that all of our specifications are realizable. All results are mechanized in the Rocq proof assistant on top of the Iris separation logic framework.»
